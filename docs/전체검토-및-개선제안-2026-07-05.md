## 1. 검토 요약

### 1.1 현 평가

코드는 모듈 분리(Tk 스레드 통합, Ollama 캐싱, 다크 테마)가 잘 잡혀 있고, `tk_root` 단일 루트 패턴과 `call_on_main` 스케줄링으로 Tkinter 스레드 안전성을 일관되게 유지하고 있다. v0.4~v0.7에 걸친 안정화 이터레이션(main loop 메인 스레드 이관, `os._exit`, pystray WNDPROC 패치 회피, onedir 빌드 전환)이 히스토리에 충실히 반영돼 있다.

반면, 검토에서 발견된 이슈 대부분은 **"동작은 하지만 위험한 패턴"** 또는 **"버전 동기화 누락"**에 집중돼 있다. 데이터 손실로 이어질 수 있는 DB 동시성 이슈가 가장 우선이다.

## 2. 🔴 Critical 이슈

### C1. SQLite 다중 스레드 동시 쓰기 — 커넥션 per-call, 잠금/무결성 보장 없음

**위치:** `config.py:29-31, 95-115`

```python
def _connect() -> sqlite3.Connection:
    return sqlite3.connect(DB_FILE)
```

`history_add`, `log_add`, `set`, `init_db` 등 모든 DB 함수가 호출마다 새 연결을 열고 `with _connect() as conn:` 블록으로 닫는다. 문제는:

- **동일 스레드 내에서도** 연결이 매번 새로 만들어지므로 트랜잭션 경계가 함수 단위로 파편화된다.
- **`drop_clipboard`는 백그라운드 스레드**에서 실행되며 그 안에서 `history_add` + `log_add`가 연달아 호출된다. 동시에 `_auto_refresh`(5s 폴러), `_ollama_check`, `_do_ollama_refresh`, `log_window`의 새로고침이 각기 다른 스레드에서 DB를 연다.
- SQLite 기본 저널 모드(rollback)에서 동시 쓰기는 `database is locked` 오류를 낸다. 운 좋게 Python `sqlite3`의 기본 `timeout=5.0`이 있어 대기 후 재시도로 넘어가는 경우가 많지만, 보장은 없다.
- 특히 `log_add`는 핫 패스(저장마다 호출)인데 1% 확률 분기 안에서 `DELETE`를 추가로 날린다. 이 시점에 다른 스레드가 쓰기를 동반하면 race window가 커진다.

**개선안:**
1. 모듈 수준 단일 커넥션 + `check_same_thread=False` + 명시적 `threading.Lock` 직렬화. 또는
2. `WAL` 저널 모드 + `busy_timeout` 설정으로 동시 읽기/단일 쓰기 허용.
3. 쓰기 전담 큐(`queue.Queue` + 단일 writer 스레드) 패턴이 가장 견고하다. 로그/히스토리를 비동기 적재하면 핫패스트(단축키 저장) 레이턴시도 줄어든다.

```python
# 예시 방향
_db_lock = threading.Lock()
_conn: sqlite3.Connection | None = None

def _connect() -> sqlite3.Connection:
    global _conn
    if _conn is None:
        _conn = sqlite3.connect(DB_FILE, check_same_thread=False, timeout=10.0)
        _conn.execute("PRAGMA journal_mode=WAL;")
        _conn.execute("PRAGMA busy_timeout=5000;")
    return _conn
```
(모든 공개 함수를 `_db_lock`으로 감싸거나 writer 큐 도입)

### C2. 설정 스펙/코드/기본값 3곳의 `ollama_model` 불일치

**위치:** `config.py:21`, `main.py:49`, `settings_window.py:82`, `기능명세.md:314`, `installer.iss:5`

| 위치 | 값 |
|------|----|
| `config.DEFAULTS["ollama_model"]` | `llama3.2` |
| `main.py` `_text_filename` 폴백 | `llama3` |
| `settings_window.py` 기본 표시 | `llama3` |
| `기능명세.md` 기본값 표 | `llama3.2` |

세 군데 하드코딩된 폴백 기본값이 서로 다르다. `config.get("ollama_model")`이 빈 문자열(사용자가 지움)을 반환하면 `or "llama3"` / `or "llama3.2"` 분기에 따라 동작이 달라진다. 동일한 단일 진실 소스(`config.DEFAULTS`)만 참조해야 한다.

**개선안:** 모든 `or "llama3..."` 폴백을 제거하고 `config.get("ollama_model")`만 사용. 빈 값일 때는 `DEFAULTS`가 이미 `llama3.2`를 반환하므로 `get()` 자체에서 정규화한다.

```python
def get(key: str) -> str:
    if key in _cache and _cache[key]:
        return _cache[key]
    ...
    return DEFAULTS.get(key, "")
```
(현재 `get`은 빈 캐시 값을 그대로 반환하므로 사용자가 빈 문자열을 저장하면 폴백이 안 된다 — 이것도 별도 마이너 이슈)

### C3. 동일 파일명 충돌 시 무조건 덮어쓰기

**위치:** `main.py:134`, `main.py:94`

```python
with open(filepath, "w", encoding="utf-8") as f:
    f.write(text)
```

파일명은 `{prefix}_{title}_{YYYYMMDD_HHMMSS}` 형식이지만 **초 단위 타임스탬프**를 쓴다. 같은 초에 두 번 저장(연속 단축키, 스크립트 자동화)하면 두 번째 저장이 첫 번째 파일을 **조용히 덮어쓴다.** 히스토리 테이블에는 서로 다른 row 2줄이 기록되지만 디스크에는 1개 파일만 남는다 → **데이터 손실 + 이력 불일치.**

이미지도 `_timestamp()`로 초 단위를 쓰므로 마찬가지 위험이 있다.

**개선안:**
- 파일명 충돌 시 자동으로 `_1`, `_2` 접미사 추가(`os.path.exists` 체크 루프), 또는
- 타임스탬프를 마이크로초/밀리초 단위로(`%Y%m%d_%H%M%S_%f`[:23] 등), 또는
- 저장 직전 `open(..., "x")` (exclusive create) 사용 후 충돌 시 재시도.

권장: 충돌 시 접미사 증가 + 토스트/로그로 알림.

## 3. 🟠 Major 이슈

### M1. 단축키 변경 시 이전 핫키 해제가 불완전 — `keyboard.remove_hotkey(hotkey_state["current"])` 는 문자열이 아닌 핸들 필요

**위치:** `main.py:389`

```python
keyboard.remove_hotkey(hotkey_state["current"])
```

`keyboard` 라이브러리의 `remove_hotkey`는 **`add_hotkey`가 반환한 핸들**(콜백 래퍼)을 받는 것이 규격이다. 문자열 hotkey를 넘기면 우연히 작동할 수는 있으나 문서화된 동작이 아니다. 핫키 변경을 반복하면 이전 등록이 누적되어 **여러 단축키가 동시에 활성화**되거나 `KeyError`가 발생할 수 있다.

**개선안:** 등록 시 핸들을 저장하고 그 핸들로 해제.

```python
hotkey_handle = keyboard.add_hotkey(...)
...
keyboard.remove_hotkey(hotkey_handle)   # 또는 keyboard.unhook_all_hotkeys()
```
`hotkey_state`를 `{"current": ..., "handle": ...}`로 확장.

### M2. Ollama 공유 캐시를 건드리는 사적인 구현체 디테일에 대한 의존

**위치:** `main.py:181-199`, `main.py:222-224`, `settings_window.py:155-158`

`_do_ollama_refresh`, `_wait_and_refresh`, `_check_ollama_status` 모두 `ollama_client._cache_lock`, `ollama_client._cached_running`, `ollama_client._cache_time`, `ollama_client._refresh_cache()` 같은 **내부 심볼**을 외부에서 직접 조작한다. 캡슐화가 깨져 있어 `ollama_client` 리팩터링 시 연쇄 파괴 위험이 크다.

**개선안:** `ollama_client`에 공개 API 추가.

```python
def set_running(running: bool, models: list[str] | None = None): ...
def force_refresh() -> bool: ...
```
외부 호출부는 이 공개 API만 사용하도록 정리.

### M3. 데드 코드 — `_setup_sleep_wake_handler` 완전 no-op + 절전 핸들러 주석만 남음

**위치:** `main.py:237-245`, 호출부 `main.py:378`

함수 본문은 로그 한 줄만 찍고 끝나며, 인자 `hotkey_state`는 쓰이지 않는다. v0.7 커밋 메시지("fix pystray WNDPROC crash")에 따라 실제 기능은 제거됐지만, 호출 인프라(`hotkey_state` dict, 호출부)가 그대로 남아 있어 "절전 복귀 시 단축키 복구"가 작동하는 것처럼 보인다.

**개선안:** 둘 중 하나.
- (a) 호출부와 함수, `hotkey_state` 파라미터를 완전히 삭제하고 명세의 "절전 핸들러 비활성화"도 현행화. 또는
- (b) `keyboard` 라이브러리는 절전 후 후킹이 끊길 수 있으므로, 안정적인 방식(예: `win32power` 또는 `WM_POWERBROADCAST`를 PyInstaller 안정성이 검증된 별도 프로세스로)으로 복구를 다시 구현.

명세(`기능명세.md:351`)와도 정합. 현재는 "제공 안 함"으로 명시돼 있으므로 (a)가 일관성 면에서 우선.

### M4. 예외 삼킴 — `restore_db` / `is_running` 등에서 예외 타입 무시

**위치:** `ollama_client.py:20-25, 143-151`, `config.py:146-158`

```python
def is_running() -> bool:
    try:
        urllib.request.urlopen(OLLAMA_URL, timeout=2)
        return True
    except Exception:
        return False
```

`urlopen`은 200이 아닌 응답(예: 404)에 대해서도 `HTTPError`를 던지지만, 200 범위라면 정상이다. 현재는 "연결만 되면 True"이므로 Ollama가 아닌 다른 서비스가 11434 포트를 점유해도 `True`로 간주한다. 또한 `URLError`의 `reason` 분기가 빠져 있어 DNS/연결 거부/타임아웃을 구분하지 못한다.

`generate_title`의 `except Exception`도 마찬가지로 너무 포괄적 — `URLError`, `socket.timeout`, `json.JSONDecodeError`, `KeyError`를 모두 하나로 묶는다.

**개선안:**
- `is_running`은 `/api/tags` 엔드포인트로 진짜 Ollama인지 검증(200 + JSON).
- 예외는 `urllib.error.URLError`/`socket.timeout`/`json.JSONDecodeError`를 구분해 로깅 레벨을 다르게.

### M5. `keyboard` 라이브러리가 윈도우 후킹에 DLL 인젝션을 쓰므로 백신/EDR 환경에서 차단 가능

**위치:** `main.py:359-375`

`keyboard`는 저수준 키보드 훅을 위해 Windows 후킹을 사용한다. 일부 AV/EDR(Kaspersky, 회사 보안 정책)에서 키로거로 오탐되어 차단되거나, 관리자 권한 요구, 또는 UAC 권한 창에서 단축키가 안 먹는 문제가 보고돼 있다. 현재 코드는 이에 대한 폴백/안내가 없다.

**개선안(Enhancement 성격):**
- 단축키 등록 실패 시 토스트/로그로 "보안 소프트웨어가 차단했을 수 있음" 안내.
- 장기적으로 `keyboard` 대신 `pynput` 또는 Win32 `RegisterHotKey`(`ctypes`/`winreg`)로 전환 검토. `RegisterHotKey`는 후킹이 아니라 OS 수준 등록이라 오탐 위험이 훨씬 낮다.

### M6. `tray.run_detached()` 스레드에서 Tk 위젯을 만드는 다크 메뉴 — 잠재적 크래시 소스

**위치:** `main.py:271-296`, `main.py:299-320`

`_dark_tray_menu`는 `tkr.call_on_main(_popup)`로 Tk 스레드에 맡기고 있어 스레드 안전성은 확보됐다. 그러나:

- `_patch_tray_dark_menu`는 `pystray._win32`의 `WM_RBUTTONUP` 핸들러를 monkey-patch하는데, pystray 버전 업그레이드 시 내부 API가 바뀌면 조용히 실패(`except Exception` → WARN 로그)하고 네이티브 메뉴로 폴백한다. 이것 자체는 안전 설계지만, 패치 성공 여부를 사용자가 알 수 없다.
- 다크 메뉴 자체가 `tk.Menu.tk_popup`을 쓰는데, 트레이 아이콘 클릭과 메뉴 팝업 사이에 타이밍 레이스가 있을 수 있다(빠른 연속 우클릭 시 이전 메뉴가 닫히기 전에 새 메뉴 생성).

**개선안:**
- 패치 실패 시 최초 1회 사용자에게 토스트로 알림(이후 세션에서는 suppress).
- `_popup` 진입 시 이미 띄워진 메뉴가 있으면 재사용하도록 가드(`_menu_ref` 싱글톤).

## 4. 🟡 Minor 이슈

### m1. 디버그 로그 파일이 커밋돼 있음 — `debug-fe40a7.log`

`git ls-files`에 `debug-fe40a7.log`(1050바이트)가 추적 중. `.gitignore`에 `*.log` 누락. 불필요한 이력 오염.

**개선:** `git rm --cached debug-fe40a7.log`, `.gitignore`에 `*.log` 추가.

### m2. 소스 파일 줄바꿈 LF/CRLF 혼재

`git diff` 경고: "LF will be replaced by CRLF". `.gitattributes`가 없어 플랫폼 간 체크아웃 시 의도치 않은 diff 발생.

**개선:** 루트에 `.gitattributes` 추가 — `* text=auto eol=lf` (또는 `*.bat text eol=crlf`, `*.py text eol=lf`).

### m3. 로그 메시지가 한국어/영어 혼재 — i18n 미적용

`config.log_add`로 쓰는 메시지(`"서버 상태 확인 중..."`, `"단축키 등록:"` 등)는 `i18n.t()`를 거치지 않고 하드코딩 한국어다. 영어 사용자 로그 창에는 한글이 섞여 나온다.

**개선:** 로그 카테고리/메시지도 i18n 키로 분리하거나, 최소한 로그는 언어 무관 영어로 통일(운영 로그는 한국어, UI는 다국어가 보통 패턴). 선택은 소유자에게.

### m4. `log_add` 1% 랜덤 정리는 비결정론적 + `init_db`에서도 정리 → 이중 정리

`config.py:55-58`(시작 시 30일 삭제)와 `config.py:111-115`(1% 확률 30일 삭제)가 중복. 랜덤 분기는 테스트/재현을 어렵게 한다.

**개선:** 시작 시 정리만 유지하고 `log_add`의 랜덤 분기 제거, 또는 주기적 타이머(예: 24시간마다) 스케줄링.

### m5. `notify._get_work_area` 캐시가 다중 모니터/DPI 변경 시 갱신 안 됨

`_work_area`는 모듈 로드 후 한 번만 계산된다. 모니터 해상도 변경, 모니터 연결/해제, DPI 스케일 변경 후 토스트 위치가 어긋날 수 있다.

**개선:** 60초 TTL 또는 `WM_DISPLAYCHANGE` 감지 시 캐시 무효화.

### m6. `resolve_model`이 폴백 목록일 때의 분기가 느슨함

`ollama_client.py:84`: `if not available or available == _FALLBACK_MODELS: return model`. `list_models()`가 실패해서 폴백을 반환한 경우, 호출자는 "진짜 설치된 모델 목록"인지 "폴백"인지 구분 불가. `list_models`가 `([], error=True)`처럼 실패를 명시적으로 반환하는 게 낫다.

### m7. `settings_window` 언어 변경 즉시 적용 누락 — "재시작 후 적용" 안내만 있음

트레이 메뉴 라벨(`pystray.MenuItem(lambda item: t(...))`)은 이미 lazy 평가이므로 언어 변경 후 다음 메뉴 오픈 시 바로 바뀐다. 그러나 이미 떠 있는 설정 창 내부 라벨은 갱신되지 않는다. 안내 문구를 개선하거나, 설정 창을 닫았다 다시 열게 유도.

## 5. 🔵 Enhancement 제안

### E1. 단축키 저장 시 단축키가 이미 시스템에 등록된 것과 충돌하는지 사전 검증
`keyboard`로는 사전 검증이 어렵지만, `RegisterHotKey` 시도로 선점 여부 확인 가능.

### E2. 저장 이력에서 파일 삭제/재저장/클립보드로 다시 복사 기능
현재 더블클릭 → 파일 열기만 지원. 우클릭 컨텍스트 메뉴로 "경로 복사", "클립보드로 불러오기", "탐색기에서 보기" 추가 제안.

### E3. 텍스트 미리보기 토스트
현재 토스트는 파일명만 표시. 저장된 텍스트 앞 1~2줄을 body에 표기하면 확인감 향상.

### E4. 이미지 OCR/AI 설명 (Ollama 멀티모달 모델 활용)
이미지 저장 시 `llava` 등 비전 모델로 파일명 생성 (`txtdrop_스크린샷_회의록_...png`). 현재는 이미지가 무조건 타임스탬프만.

### E5. 자동시작 레지스트리 등록을 인앱에서 토글
`installer.iss`의 `[Tasks] startup`은 설치 시 1회만. 설정 창에 "Windows 시작 시 실행" 체크박스 + `winreg`로 `HKCU\...\Run` 토글 권장.

### E6. 단일 인스턴스 락
현재 두 번 실행하면 트레이 아이콘이 2개 생기고 단축키가 충돌한다. 시작 시 `mutex`(Win32 `CreateMutex`)로 선점 체크. 두 번째 실행은 이미 떠 있는 창을 활성화하고 종료.

### E7. 패키징 — `requirements.txt`에 고정 버전 + `pip-tools` 또는 `uv lock`
현재 `>=` 최소 버전만. 재현 가능 빌드를 위해 lock 파일 도입.

### E8. 코드 서명
인스톨러/EXE가 서명돼 있지 않아 SmartScreen 경고 표시. 자체 서명이라도 추가하면 사용자 신뢰도 향상.
